Como usar este guia

Leia aula por aula ou use o menu para ir diretamente a um assunto. Cada aula apresenta o commit, os conceitos, uma prática, a conferência da revisão e prompts para aprofundar o estudo com um agente.

O fio condutor é a Pousada Parnaioca: começamos com uma API de dados e avançamos até um assistente que consulta funções, recupera documentos e acessa ferramentas via MCP. O conteúdo foi reconstruído dos nove commits do repositório, da base inicial até 7accf8e.

Leitura histórica: “neste commit” descreve o código daquela aula. Os comandos HTTP de prática indicam quando usam a versão atual. Explicações e exercícios ampliam os conceitos registrados no histórico; não pressupõem conteúdo de aula que não aparece nos arquivos.

Aula 00

Base do projeto: API da pousada

Commit 24214ea 09/09/2026
Objetivo da aula

Executar a API e entender os dados que, mais tarde, serão consultados pelo agente.

O que mudou neste commit

O boilerplate cria o servidor Express, TypeScript, três coleções JSON, tipos de domínio, configurações, README e cinco PDFs. São 12 hóspedes, 8 quartos e 18 reservas. A inteligência artificial ainda não é chamada nesta etapa.

Node.js, TypeScript, Express e módulos ES

Node.js executa JavaScript fora do navegador. TypeScript descreve os formatos dos dados e detecta incompatibilidades na compilação. Express recebe requisições HTTP e organiza as rotas. O projeto requer Node.js 24 ou superior; type: "module" ativa módulos ES, com import e export.

tsx executa TypeScript no desenvolvimento. tsc verifica tipos e gera JavaScript em dist. O tsconfig.json usa NodeNext, strict, noUncheckedIndexedAccess e exactOptionalPropertyTypes. Imports locais terminam em .js para funcionar também no código compilado.

Instalação e comandos

Na base inicial, a porta é Number(process.env.PORT) || 8000. dev reinicia ao salvar; start executa uma vez; prod depende do build. express.json() interpreta corpos JSON.

Hóspedes, quartos e reservas

Tipo Papel Campos relevantes
Guest Hóspede id, name, email, phone, city, preferences
Bedroom Quarto id, name, description, capacity, price, amenities
Reservation Reserva guestId, bedroomId, checkinAt, checkoutAt, guests, price, status, specialRequests

A reserva referencia o hóspede e o quarto pelos IDs. getPopulatedReservations() combina map e find para devolver os objetos completos. O tipo PopulatedReservation usa Omit para remover as referências e acrescenta guest e bedroom. O campo numérico reservation.guests indica a quantidade de pessoas; a coleção guests contém registros de hóspedes.

Rotas HTTP e envelope da resposta

Rota Retorno
GET /health data.status igual a ok
GET /guests Lista de hóspedes
GET /bedrooms Lista de quartos
GET /reservations Reservas com guest e bedroom populados

As respostas usam { message, data }. Os JSON são dados de demonstração, não um banco persistente. A asserção as Guest[] informa um tipo ao compilador, mas não valida o arquivo em tempo de execução. Um relacionamento inexistente provoca o erro explícito da função de população.

Prática guiada

Localize reservation-001: ela se relaciona com guest-001 (João Silva) e bedroom-008 (Suíte Caxadaço). Compare a resposta com o JSON original.

Revisão e conferência

  • Por que popular uma reserva? Conferência: para entregar os objetos relacionados sem obrigar o cliente a fazer novas consultas.
  • O que ocorre se um ID não existir? Conferência: a função lança um erro; a tipagem não garante integridade dos JSON.
  • Como trocar a porta? Conferência: informe PORT no ambiente, por exemplo PORT=3000 npm start.

Arquivos para estudar

src/index.ts, src/types.ts, src/data/index.ts, src/data/*.json, tsconfig.json, package.json, .env.example, .gitignore, README.md e os PDFs de docs.

O que mudou neste commit

Biblioteca, modelo e serviço

O pacote openai é o SDK usado pelo programa para conversar com a API. O modelo é o componente que processa a entrada e produz uma saída; ele não está instalado em node_modules. package.json e lockfile

Para estudar o projeto já clonado, npm install instala as dependências existentes; não é necessário adicionar novamente o SDK. npm ci reproduz a instalação pelo lockfile quando os dois arquivos estão sincronizados.

O nome de modelo encontrado nos exemplos é um registro do curso. Ao executar chamadas, configure OPENAI_MODEL com um modelo disponível na sua conta. Scripts históricos podem ter o nome fixo no código. O guia funciona sem chave.

Aula 02

LLMs, tokens, contexto e prompt engineering

Commit 8edbaa4 15/09/2026
Objetivo da aula

Fazer a primeira chamada e entender como dados, instruções e consumo de tokens afetam a resposta.

O que mudou neste commit

Adiciona dotenv e src/first-call.ts. O script reúne guests, reservations e bedrooms, serializa os dados e envia uma pergunta para client.responses.create. Imprime output_text e usage.

LLM e limites das respostas

Um modelo de linguagem gera respostas a partir da entrada recebida e dos padrões aprendidos no treinamento. Ele não consulta automaticamente os JSON da pousada e não sabe o estado atual das reservas. Nesta aula, o programa coloca os dados dentro do prompt.

A pergunta original pede uma sugestão sobre quando João fará uma nova reserva além das já existentes. Isso é uma hipótese, não um fato verificável no cadastro. Diferencie uma reserva registrada, uma inferência apoiada em padrões e uma previsão incerta. Peça que o agente declare essa diferença.

Tokens, uso e janela de contexto

Tokens são unidades usadas para representar texto na entrada e na saída; não correspondem sempre a uma palavra. Dados JSON, instruções, histórico e resultados de ferramentas também ocupam espaço. response.usage permite observar o consumo da chamada. Mais dados podem aumentar custo, tempo e dificuldade de localizar o que importa.

A janela de contexto limita quanto cabe em uma chamada. Ela depende do modelo e da configuração. O comentário sobre “272k” encontrado posteriormente no código é uma anotação da aula, não uma garantia aplicável a todos os modelos.

Cliente, input e output_text

O trecho resume o fluxo; context representa os dados carregados. await espera a resposta remota. output_text é o texto agregado e usage são os dados de uso. O código histórico usa um modelo fixo; a versão atual lê OPENAI_MODEL.

Prompt engineering: papel, tarefa, dados e limites

Um prompt útil informa o objetivo, fornece os dados necessários e define como responder quando faltar informação. Para a pousada, diga qual é a data de referência ao perguntar pela “próxima” reserva. Defina critérios observáveis, como desconsiderar reservas canceladas, em vez de esperar que o modelo adivinhe.

Prática guiada

Configure a chave antes. No commit da aula 02, compare texto e uso. Na versão atual, o script faz duas chamadas independentes: a primeira envia hóspedes e reservas; a segunda pergunta o nome do quarto sem reenviar os dados ou conectar as respostas. Ele demonstra a ausência de continuidade automática.

Revisão e conferência

  • O modelo lê arquivos locais sozinho? Conferência: não; o programa deve enviar os dados ou disponibilizar ferramentas.
  • Uma previsão é uma reserva? Conferência: não; a previsão deve ser apresentada como hipótese.
  • Por que reduzir o JSON enviado? Conferência: para diminuir entrada e concentrar a resposta nos dados relevantes.

Arquivos para estudar

src/first-call.ts, src/data/*.json, package.json.

Aula 03

User prompt, few-shot e saída estruturada com Zod

Commit ef6109b 16/09/2026
Objetivo da aula

Transformar uma avaliação livre em dados tipados e distinguir validação de entrada da estrutura da saída.

O que mudou neste commit

Instala Zod, cria review.schema.ts e adiciona POST /review/analyze e POST /chat. A análise usa responses.parse, zodTextFormat e exemplos few-shot. O chat inicial usa um array global compartilhado.

Instruções, user prompt e exemplos few-shot

instructions define a tarefa e os critérios: avaliar hóspedes, considerar o impacto de reclamações e selecionar a categoria do problema principal. A mensagem com role: "user" fornece a avaliação. Mensagens de assistant com respostas de exemplo demonstram como classificar; esse padrão é chamado few-shot.

O exemplo “a praia é linda, mas esperei duas horas” recebe sentimento negativo, categoria service e prioridade high. Ele ensina que um elogio não elimina um problema relevante. Exemplos ajudam a orientar o resultado, mas ainda é necessário avaliar casos novos e ambíguos.

Schema, enums e inferência de tipos

Zod descreve e valida valores em execução. z.infer deriva o tipo TypeScript do schema, evitando manter dois contratos à mão. No commit original, o nome é reviewAnalyzeSchema; na aula 08 ele vira reviewAnalysisSchema. Os valores dos enums permanecem os mesmos.

Structured Output e responses.parse

Pedir “responda em JSON” no texto não estabelece sozinho um contrato de saída. Aqui, o schema é enviado como formato estruturado e o SDK entrega output_parsed. Um objeto bem formado pode ter uma classificação discutível: conformidade estrutural e acerto semântico são coisas diferentes.

A versão atual trata a ausência de output_parsed com HTTP 422. Também valida o corpo com analyzeReviewSchema. Na aula 03, a entrada tinha somente uma verificação simples de presença.

Primeiro chat e suas limitações

O array global context: any = [] acumula user e assistant. Assim, requisições posteriores recebem as mensagens anteriores. Contudo, todos os usuários compartilham a mesma lista e o histórico desaparece ao reiniciar. Os limites de tamanho não são tratados. Isso motiva a separação por conversa na aula 05.

As instruções de restrição ao domínio da pousada estão comentadas no chat deste commit. Não considere o comentário como uma regra executada. Na versão atual, a rota de análise usa o plural: /reviews/analyze.

Prática guiada

No commit da aula 03, use /review/analyze. Confira se a resposta contém somente valores previstos no schema. Experimente uma avaliação mista e justifique a categoria; a classificação é produzida pelo modelo.

Revisão e conferência

  • Qual o papel do few-shot? Conferência: mostrar exemplos de entrada e resposta para orientar os critérios.
  • Schema garante uma avaliação correta? Conferência: garante o formato esperado quando há saída válida, mas não substitui a avaliação do conteúdo.
  • Por que o array global é problemático? Conferência: mistura conversas e cresce sem controle.

Arquivos para estudar

src/index.ts e src/review.schema.ts; consulte git show ef6109b:src/index.ts para a implementação original.

Aula 04

Tool calling e agent loop

Commit 328ed42 21/09/2026
Objetivo da aula

Entender como o modelo pede uma consulta e como o programa executa a ferramenta e devolve o resultado.

O que mudou neste commit

Cria src/tool-calling.ts com findGuest, findReservationsByGuestId, schemas de ferramentas, dispatch por nome e um loop limitado. Neste commit, o agente é executado diretamente com uma pergunta fixa; ainda não está conectado à rota /chat.

Contrato da ferramenta e função real

A ferramenta anunciada ao modelo contém nome, descrição e parâmetros em JSON Schema. O handler é a função JavaScript que efetivamente acessa os dados. O modelo solicita uma execução com function_call; o programa decide como realizá-la. A descrição deve explicar quando usar a ferramenta e o significado dos argumentos.

strict: true orienta a geração conforme o contrato. Ainda assim, os handlers verificam argumentos e tratam falhas. findGuest busca por parte do nome, sem diferenciar maiúsculas; usa find, portanto retorna o primeiro resultado e não resolve ambiguidades entre homônimos.

Rodadas, function_call e call_id

Pergunta → modelo → chamada de ferramenta → handler → resultado → modelo → resposta final

O agente começa com a pergunta. Se houver uma chamada, executa o handler, acrescenta a chamada e seu resultado à entrada e consulta o modelo novamente. Para reservas de João, primeiro pode obter o guestId e depois filtrar as reservas. Isso evita enviar todas as coleções em toda pergunta.

call_id associa o resultado à solicitação correta. A saída da ferramenta é serializada como texto. Quando a rodada não contém function_call, o código retorna response.output_text.

Limites e tratamento de erros

MAX_ROUNDS = 5 limita consultas ao modelo e MAX_TOOL_CALLS = 10 limita execuções de funções por execução do agente. Uma rodada pode conter mais de uma ferramenta. Esses limites evitam ciclos indefinidos, mas não equivalem a timeout, orçamento financeiro ou política de autorização.

executeTool faz dispatch pelo nome, interpreta argumentos JSON e devolve objetos de erro em caso de falha. O modelo recebe esses erros para poder explicar a limitação. A busca por hóspede inexistente também precisa de uma resposta clara; é um bom ponto para discutir normalização para null.

Prática guiada

Nesse commit, npx tsx src/tool-calling.ts executa a pergunta fixa sobre a próxima reserva de João em 6 de setembro de 2026. Na versão atual, o arquivo exporta runAgent; executá-lo sozinho não faz essa pergunta. Use a rota /chat após a configuração descrita na aula 08.

Revisão e conferência

  • Quem executa a função? Conferência: o programa, após receber o pedido do modelo.
  • Por que usar call_id? Conferência: vincular saída e chamada.
  • Como o loop termina? Conferência: quando não há function_call ou quando os limites são atingidos.

Arquivos para estudar

src/tool-calling.ts e src/data/index.ts.

Aula 05

Histórico de conversa versus contexto

Commit 823bcd5 23/09/2026
Objetivo da aula

Manter a continuidade por conversa e preservar os itens necessários para novas rodadas do agente.

O que mudou neste commit

Conecta runAgent à rota /chat, cria chat.schema.ts e validation.middleware.ts, armazena conversas em Map e adiciona getBedroomById. Passa a converter a saída com toResponseInputItems.

O que é histórico e o que é contexto

Histórico é o registro das mensagens e eventos anteriores. Contexto é o conjunto efetivamente recebido pelo modelo em uma chamada: instruções, parte do histórico, dados e resultados de ferramentas. Guardar mensagens no servidor não significa que o modelo recebeu essas mensagens. Nesta implementação, o programa copia o histórico salvo para input.

Isso permite a pergunta “qual é o nome do quarto?” depois de uma consulta de reservas, desde que o mesmo conversationId seja usado. A ferramenta getBedroomById resolve o bedroomId. Sem reenvio ou outra forma explícita de continuidade, uma nova chamada é independente.

Map, conversationId e itens de resposta

O Map separa listas por identificador. toResponseInputItems converte a saída completa em itens reutilizáveis, preservando mensagens e chamadas necessárias à continuidade. Não basta guardar somente output_text quando o protocolo inclui ferramentas. O histórico só é salvo no caminho de conclusão normal.

Middleware e safeParse

chatSchema exige message e conversationId como strings; trim() remove espaços das extremidades e min(1) rejeita strings vazias. safeParse retorna sucesso ou falha sem exigir uma exceção como fluxo normal.

O middleware responde HTTP 400 com campo e mensagem em caso de erro. Em caso de sucesso, salva os dados tratados em res.locals.validation e chama next(). A rota deve consumir esse resultado, não voltar ao corpo bruto.

Memória, isolamento e crescimento

O Map é temporário: perde dados quando o processo reinicia. O código não implementa expiração, resumo, corte de mensagens nem coordenação de requisições simultâneas da mesma conversa. Histórico crescente consome mais tokens. Na aula 06 a chave passa a incluir o usuário para evitar que dois usuários compartilhem o mesmo identificador.

Nesta aula ainda não existe autenticação. Nos exemplos executáveis da versão atual, envie Bearer token; a chave atual do histórico é userId:conversationId.

Prática guiada

Repita a segunda pergunta com outro conversationId e compare. Não dependa de uma resposta literal: observe se o agente precisa pedir esclarecimento e quais ferramentas ele usa.

Revisão e conferência

  • Histórico salvo é contexto automaticamente? Conferência: não; é necessário incluí-lo na chamada.
  • Por que usar os dados de res.locals? Conferência: são os valores já validados e transformados.
  • O Map persiste após reinício? Conferência: não.

Arquivos para estudar

src/chat.schema.ts, src/validation.middleware.ts, src/tool-calling.ts e src/index.ts.

Aula 06

Segurança e Human in the Loop

Commit 9181b14 28/09/2026
Objetivo da aula

Aplicar permissões no código e separar solicitação de cancelamento da decisão humana.

O que mudou neste commit

Cria auth.middleware.ts e approval.store.ts, protege /chat, acrescenta permissões por perfil e POST /approvals/:approvalId. O histórico passa a usar userId:conversationId. Embora o título mencione RAG iniciado, o diff desta aula ainda não cria ingestão ou busca documental; elas entram na aula 07.

Autenticação e autorização

Autenticação identifica o usuário; autorização decide o que ele pode fazer. O middleware lê Authorization: Bearer ..., consulta um mapa de tokens demonstrativos e grava { userId, role } em res.locals.auth. Token ausente ou desconhecido recebe HTTP 401. Um usuário autenticado sem permissão recebe HTTP 403 na decisão de aprovação.

Perfil Token demonstrativo Ferramentas de função
guest guest-demo-token getBedroomById
employee employee-demo-token findGuest, findReservationsByGuestId, getBedroomById, requestReservationCancellation
manager manager-demo-token As mesmas do employee; também pode decidir a aprovação na rota HTTP

Uma instrução de prompt não substitui a checagem no servidor. isToolAllowed é chamado antes do handler. Nesta aula, todas as ferramentas ainda são anunciadas ao modelo, mas execuções não permitidas são bloqueadas; na aula 08 o anúncio também será filtrado.

Solicitar, aprovar e rejeitar

Funcionário solicita → aprovação pending → gerente decide → approved cancela / rejected preserva

requestReservationCancellation verifica se a reserva existe e se não está completed ou cancelled. Cria um UUID, registra requestedBy e createdAt e mantém o status pending. A ferramenta retorna o ID para encaminhamento ao gerente; ela não altera imediatamente a reserva.

decideCancellation aceita apenas solicitações pendentes, registra decidedBy e decidedAt e muda a reserva para cancelled somente quando a decisão é approved. A rota permite a decisão exclusivamente ao perfil manager. O exemplo não suspende o loop até o humano responder: ele termina com a solicitação pendente e a decisão ocorre por uma requisição posterior.

Isolamento e limites da demonstração

A chave composta separa usuários que escolhem o mesmo conversationId. Aprovações e histórico ficam em memória; mudanças na coleção de reservas não são gravadas no JSON. Os tokens são fixos e conhecidos, úteis para experimentar perfis. O código não oferece autenticação real, auditoria persistente nem regra de propriedade por hóspede.

Observe o alcance concreto: as rotas GET de hóspedes, quartos e reservas continuam públicas no projeto, assim como a análise de avaliações. O controle das ferramentas do chat não protege automaticamente esses outros caminhos. O estudo de segurança deve considerar cada rota e cada fonte de dados.

Prática guiada

  • Rejeitar muda o status da reserva? Conferência: não; somente aprovar muda para cancelled.

RAG, embeddings, chunks e base de conhecimento

Commit 5aeb73d 30/09/2026
Objetivo da aula

Indexar documentos e buscar trechos relevantes antes de tentar gerar uma resposta documental.

O que mudou neste commit

Cria ingest-documents.ts e search-documents.ts e os comandos rag:ingest e rag:search. Separa quatro PDFs públicos do manual interno. A busca desta aula retorna trechos; a geração com file_search só será implementada na aula 08.

RAG e embeddings

RAG combina recuperação de informação com geração: a pergunta orienta uma busca e os trechos encontrados sustentam a resposta do modelo. Isso evita anexar todos os documentos em toda requisição. Embeddings representam conteúdo como vetores para comparar proximidade semântica. Uma busca pode recuperar ideias relacionadas mesmo sem a mesma sequência de palavras.

No projeto, o processamento e a representação vetorial são gerenciados pelo serviço de vector stores. O código não calcula embeddings manualmente, não chama uma API de embeddings diretamente e não treina o modelo com os PDFs. Ingestão é preparação de uma base pesquisável.

Chunks e sobreposição

Um chunk é um trecho do documento. O tamanho máximo de 800 tokens evita tratar um PDF inteiro como uma única unidade. A sobreposição de 200 tokens mantém parte do contexto nas fronteiras. Sobreposição pode melhorar a recuperação de informações que atravessam cortes, mas também repete conteúdo e aumenta armazenamento. Essas são escolhas deste curso, não valores universais.

Upload, vector stores e polling

uploadDocuments abre streams dos PDFs e usa Promise.all para enviar arquivos com purpose: "assistants". createKnowledgeBase cria um vector store, associa os arquivos com fileBatches.createAndPoll e espera o processamento. O código verifica status completed e quantidade de falhas antes de considerar a base pronta.

Base Arquivos
Pública cancelamento.pdf, politica-hospedagem.pdf, passeios.pdf, faq.pdf
Interna manual-funcionarios.pdf

Os stores têm expiração de 30 dias após a última atividade, conforme a configuração. Ao terminar, o script imprime os IDs a adicionar ao .env. Cada execução cria novas bases e envia arquivos novamente; não há reutilização automática. O bloco comentado de limpeza manual que existia neste commit foi removido na aula 08.

Busca direta, scores e qualidade

O script exige audience public ou internal e uma pergunta. Escolhe o store correspondente e mostra arquivo, score e texto. rewrite_query permite a reescrita da consulta pelo serviço. O score ajuda a ordenar relevância, mas não deve ser tratado como uma probabilidade de a resposta estar correta.

Confira se o trecho realmente responde à pergunta, se a origem é adequada ao perfil e se há informação suficiente. O comando de busca interna é uma ferramenta de desenvolvedor com acesso ao ambiente; não implementa sozinho autenticação de usuário. A separação por perfil no chat chega na aula 08.

Prática guiada

A ingestão envia PDFs para o serviço usando sua conta. Faça-a quando precisar criar as bases. Em seguida, procure as respostas nos trechos retornados e registre o nome do documento; nesta etapa não espere uma resposta final em linguagem natural.

  • RAG treina o modelo com os PDFs? Conferência: não nesta implementação; indexa e recupera documentos.
  • Qual a diferença entre chunk e embedding? Conferência: chunk é o trecho; embedding é uma representação vetorial do conteúdo.
  • rag:search já responde como assistente? Conferência: não; mostra evidências recuperadas.

Aula 08

RAG no agente, MCP e frameworks

Commit 7accf8e 02/10/2026
Objetivo da aula

Integrar busca documental ao chat, expor ferramentas via MCP e comparar um loop manual com um framework de agentes.

O que mudou neste commit

Adiciona file_search, filtragem de ferramentas por perfil, servidores e clientes MCP via stdio e Streamable HTTP, um agente MCP manual, exemplo com Agents SDK e exemplos de API e SQLite. Atualiza first-call, validações, modelo configurável e a rota /reviews/analyze.

Configuração atual e ordem de execução

O .env.example original só lista chave e modelo; acrescente os dois IDs manualmente. tool-calling.ts exige os IDs ao ser importado pelo servidor. Assim, mesmo uma consulta a /health depende de o processo conseguir iniciar com essa configuração. O guia é servido por um comando independente e não precisa de nenhuma variável de IA.

file_search: da recuperação à resposta

src/rag/file-search.ts faz uma chamada Responses com a ferramenta hospedada file_search apontando para a base pública. Recebe uma pergunta por argumentos do terminal, limita os resultados a três e pede include: ["file_search_call.results"] para inspecionar as evidências no output.

No chat, getToolsForRole combina funções permitidas e file_search. Hóspedes recebem apenas o store público; employee e manager recebem público e interno. As chamadas de busca são executadas pelo serviço: o loop local registra file_search_call, mas não cria manualmente um function_call_output para essa ferramenta. As functions locais continuam passando pelos handlers e por suas permissões.

Use funções para registros estruturados e file_search para políticas, passeios, perguntas frequentes e procedimentos. Peça que o agente diga quando não há informação. A busca reduz a necessidade de incluir documentos inteiros, mas não elimina erros de recuperação ou interpretação.

MCP: servidor, cliente, tools e resources

MCP (Model Context Protocol) define uma forma de um cliente descobrir e acessar capacidades de um servidor. O servidor expõe funções e recursos; o cliente estabelece a conexão e usa essas capacidades. MCP não é um modelo de linguagem. O cliente demonstrativo consulta dados sem fazer chamada à OpenAI.

Capacidade neste projeto Uso
Tool find_guest Busca hóspede pelo nome; entrada validada com Zod; devolve conteúdo textual com JSON ou null
Resource bedrooms-catalog Catálogo JSON em parnaioca://bedrooms/catalog
listTools / callTool Descobrir ferramentas e executar uma chamada
listResources / readResource Listar e ler recursos disponibilizados

createParnaiocaMcpServer() concentra os registros para reutilização nos dois transportes. O catálogo é um recurso legível, enquanto find_guest é uma função executável. Não há prompts MCP registrados neste projeto.

Transporte stdio e ciclo de vida

StdioClientTransport inicia o processo servidor com npx tsx src/mcp/server.ts. Os processos trocam mensagens por stdin/stdout. Por isso, o servidor usa console.error para o log: stdout deve ser reservado ao protocolo.

O cliente lista ferramentas, consulta João, tenta uma ferramenta inexistente, lista recursos e lê o catálogo. Fecha a conexão em finally. Não é necessário iniciar mcp:server em outro terminal: o cliente já cria seu servidor filho. O comando mcp:server existe para iniciar o servidor stdio diretamente, que ficará aguardando mensagens do protocolo.

Transporte Streamable HTTP

O servidor escuta em 127.0.0.1:8001/mcp e recebe os métodos HTTP pelo handler MCP. createMcpExpressApp, createMcpHandler e toNodeHandler adaptam protocolo, Express e Node. O cliente usa StreamableHTTPClientTransport, lista ferramentas e chama find_guest.

stdio Streamable HTTP
Processo filho iniciado pelo cliente Servidor iniciado separadamente
stdin/stdout; sem URL HTTP URL HTTP /mcp
Útil para conexão local entre processos Permite conexão através de HTTP; este exemplo limita o bind ao loopback

O exemplo HTTP não adiciona o authMiddleware da API da pousada. Nem ele nem o servidor stdio implementam a matriz de perfis do chat. As permissões da aplicação não são transferidas automaticamente a um novo servidor MCP.

Agente manual com ferramentas descobertas

src/mcp/agent.ts conecta por stdio, descobre ferramentas e converte cada inputSchema em parâmetros de uma function tool da Responses. O conversor usa strict: false. O modelo solicita uma função e o programa encaminha para mcpClient.callTool. O resultado volta como function_call_output com o call_id original.

O loop tem até cinco rodadas, reaproveita a saída com toResponseInputItems e encerra quando não há chamadas de função. O agente pergunta se João está cadastrado e qual seu e-mail. Ele expõe tools descobertas, mas não transforma o resource do catálogo em ferramenta do modelo. Ao final, fecha o cliente em finally.

Agents SDK e responsabilidades do framework

src/frameworks/agents-sdk.ts usa MCPServerStdio, Agent e run. O agente recebe instructions, model e mcpServers; o framework gerencia a execução e entrega result.finalOutput. cacheToolsList: true reaproveita a descoberta das ferramentas, e o servidor é fechado em finally.

O loop manual torna visíveis chamadas, resultados e limites. O framework reduz o código de orquestração. Em ambos, regras de acesso, validação de domínio, qualidade dos dados e aprovação de ações continuam responsabilidades da aplicação. O exemplo de framework não incorpora o fluxo de cancelamento do chat.

Ferramentas sobre API e banco de dados

api-tools.ts consulta http://localhost:8000/bedrooms com fetch, verifica response.ok, extrai data e imprime uma tabela. Depende da API em execução. A asserção de tipo do corpo não é uma validação de runtime.

database-tools.ts cria SQLite em memória com DatabaseSync, carrega hóspedes, quartos e reservas e executa uma consulta com LEFT JOIN. O filtro de nome usa placeholder ? e parâmetro vinculado; não concatena o nome no SQL. Fecha o banco em finally. O banco não é persistido em disco.

Esses dois scripts chamam funções diretamente. Seus nomes ilustram possíveis handlers, mas não registram ferramentas na OpenAI ou no MCP. A origem de dados pode mudar sem mudar a ideia central: validar argumentos, consultar e devolver um resultado controlado.
